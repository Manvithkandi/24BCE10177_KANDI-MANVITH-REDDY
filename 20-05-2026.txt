/*
When you use ADD CONSTRAINT, the database expects you to add one specific rule
 at a time, and you have to tell it exactly which column that rule applies to 
 (for example, UNIQUE(age)).

Furthermore, databases usually don't let you use ADD CONSTRAINT for NOT NULL. They
 treat NOT NULL as a core property of the column itself, not as an add-on constraint.

If you want to apply all three rules (NOT NULL, UNIQUE, and CHECK) to an existing 
column in a single line, you skip ADD CONSTRAINT and instead redefine the column using
 MODIFY (in MySQL/Oracle).

If constraint A was created as a named constraint (like ADD CONSTRAINT chk_old_age CHECK
...), it will not vanish when you run a MODIFY statement. It will stay active in the background
 alongside your new rules (B, C, and D).

This creates a hidden conflict. If constraint A requires age >= 10 and your new constraint B 
requires age >= 18, both are checked. If they ever contradict each other, you won't be able to 
insert any data at all.

Why does this happen?
Databases separate column properties from table constraints:

Column Properties (like NOT NULL or data types) do get overwritten by MODIFY.

Table Constraints (like CHECK or UNIQUE) are stored as separate objects in the 
database's system catalog. MODIFY does not automatically delete those objects.

The Right Way to Switch Rules
To get rid of constraint A completely and replace it with B, C, and D, you must drop 
the old one first.

SQL
-- 1. Get rid of the old constraint (A)
ALTER TABLE Persons DROP CONSTRAINT chk_old_age;

-- 2. Apply your new rules (B, C, and D) in a single line
ALTER TABLE Persons MODIFY age INT NOT NULL UNIQUE CHECK (age >= 18);
*/
